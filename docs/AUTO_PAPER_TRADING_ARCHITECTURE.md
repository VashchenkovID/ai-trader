## Обзор

### Проблема

Текущая система требует ручного подтверждения и исполнения всех торговых заявок, что:
- Ограничивает скорость сбора данных для обучения моделей
- Замедляет адаптацию моделей к изменениям рынка
- Не позволяет RL-модели получать опыт в реальном времени
- Создает задержку в обновлении весов моделей

### Решение

Реализация автоматической торговли в paper режиме для:
- Ускорения сбора данных для обучения
- Непрерывного обучения RL-модели в реальном времени
- Быстрой адаптации весов моделей на основе результатов
- Тестирования стратегий без риска для реального капитала

### Ключевые оптимизации для максимального сбора данных

1. **Виртуальный портфель: 50-75 млн рублей** (оптимальный диапазон)
   - 50 млн - минимум для максимальной эффективности (12 позиций)
   - 75 млн - максимум с запасом для дорогих инструментов
   - Дальнейшее увеличение не дает прироста в количестве позиций

2. **Лимиты для paper режима:**
   - maxTotalExposure: 60% (было 40%) - для максимизации параллельных позиций
   - maxPositionSize: 5% (без изменений)
   - Результат: до 12 позиций одновременно (вместо 8)

3. **Частота обновлений:**
   - Кеш: каждые 2 часа (было 4)
   - Анализ портфеля: каждый час (было 2)

### Принципы

1. **Безопасность**: Полная изоляция от реального портфеля
2. **Реалистичность**: Симуляция реальных условий торговли
3. **Контролируемость**: Возможность остановки и настройки
4. **Прозрачность**: Полное логирование всех действий
5. **Постепенность**: Поэтапное внедрение с валидацией

## Цели и задачи

### Основные цели

1. **Ускорение обучения моделей**:
   - Увеличение количества сделок в 2-3 раза
   - Сбор данных в 2-3 раза быстрее
   - Обновление весов моделей в 3-7 раз чаще

2. **Улучшение качества обучения**:
   - RL-модель получает опыт в реальном времени
   - Быстрая адаптация к изменениям рынка
   - Больше разнообразных сценариев для обучения

3. **Оптимизация процесса**:
   - Автоматизация рутинных операций
   - Снижение нагрузки на пользователя
   - Непрерывное улучшение моделей

### Задачи

1. Создать систему автоматического исполнения заявок в paper режиме
2. Реализовать реалистичную симуляцию исполнения (спреды, проскальзывание)
3. Интегрировать с существующими сервисами (FeedbackService, ModelWeightingService)
4. Обеспечить безопасность и изоляцию от реального портфеля
5. Создать систему мониторинга и контроля
6. **Увеличить виртуальный портфель до 50-75 млн рублей** (оптимальный диапазон для максимального сбора данных)
7. **Увеличить лимит экспозиции для paper режима до 60%** (для максимизации параллельных позиций)
8. Оптимизировать частоту обновления кеша и анализа для улучшения качества рекомендаций

## Процессы и потоки данных

### Процесс 1: Создание и автоматическое исполнение заявки

```
1. AI-модели генерируют рекомендацию
   ↓
2. TradingRequestService.createTradingRequest()
   - Создает заявку со статусом PENDING
   - Валидация через RiskManagementService
   ↓
3. AutoPaperTradingService.processNewRequest()
   - Проверка canAutoExecute()
   - Если да → autoExecuteRequest()
   ↓
4. RealisticExecutionSimulator.simulateExecution()
   - Расчет спреда, проскальзывания, комиссии
   - Возврат executionResult
   ↓
5. TradingEngine.executePaperOrder()
   - Исполнение с executionResult
   - Обновление виртуального портфеля
   - Возврат tradeResult
   ↓
6. TradingRequest.execute()
   - Обновление статуса на EXECUTED
   - Сохранение actualPrice, actualAmount, commission
   - Сохранение executionResult
   ↓
7. FeedbackService.recordTradeResult()
   - Запись результата
   - Обновление весов моделей
   ↓
8. ReinforcementLearningService.incrementalTrainFromTrades()
   - Инкрементальное обучение на результате
```

### Процесс 2: Проверка условий автоматического исполнения

```
canAutoExecute(tradingRequest):
  ├─ Проверка режима: tradingMode === 'paper'?
  ├─ Проверка флага: isEnabled === true?
  ├─ Проверка confidence: >= minConfidence?
  ├─ Проверка score: 
  │   ├─ BUY: score >= minScore?
  │   └─ SELL: score <= maxScore?
  ├─ Проверка лимитов:
  │   ├─ dailyTrades < maxDailyTrades?
  │   ├─ timeSinceLastTrade >= minTimeBetweenTrades?
  │   └─ dailyPnL > -maxDailyLoss?
  ├─ Проверка размера позиции: <= maxPositionSize?
  └─ Проверка рисков через RiskManagementService
```

### Процесс 3: Симуляция реалистичного исполнения

```
simulateExecution(order, marketData):
  ├─ Определение ликвидности: getLiquidityLevel()
  ├─ Расчет спреда: calculateSpread()
  ├─ Расчет проскальзывания: calculateSlippage()
  ├─ Расчет цены исполнения:
  │   ├─ BUY: price + spread + slippage
  │   └─ SELL: price - spread - slippage
  ├─ Проверка частичного исполнения: checkPartialFill()
  ├─ Расчет комиссии
  └─ Возврат: { executedPrice, executedQuantity, commission, slippage, spread }
```

## Риски и митигация

### Риск 1: Переобучение на виртуальных данных

**Описание**: Модели могут переобучиться на особенностях виртуальной торговли, которые не применимы к реальной.

**Митигация**:
- Реалистичная симуляция исполнения (спреды, проскальзывание)
- Регулярное сравнение с ручным режимом
- Ограничение автоматизации только paper режимом
- Мониторинг различий между виртуальной и реальной торговлей

**Метрики**:
- Сравнение производительности виртуальной и реальной торговли
- Анализ различий в результатах

### Риск 2: Ошибки в логике автоматического исполнения

**Описание**: Баги в коде могут привести к неправильному исполнению заявок.

**Митигация**:
- Тщательное тестирование перед внедрением
- Множественные проверки перед исполнением
- Логирование всех действий
- Возможность быстрого отключения
- Изоляция от реального портфеля

**Метрики**:
- Количество ошибок при автоматическом исполнении
- Процент успешных исполнений

### Риск 3: Слишком агрессивная торговля

**Описание**: Система может торговать слишком часто, что приведет к избыточным комиссиям и переобучению.

**Митигация**:
- Лимиты на количество сделок в день
- Минимальный интервал между сделками
- Проверка лимитов риска
- Мониторинг частоты торговли

**Метрики**:
- Среднее количество сделок в день
- Процент от общего количества заявок

### Риск 4: Низкое качество данных для обучения

**Описание**: Автоматически исполненные заявки могут быть низкого качества, что ухудшит обучение моделей.

**Митигация**:
- Фильтрация заявок по confidence и score
- Валидация через RiskManagementService
- Анализ качества данных перед обучением
- Возможность исключения низкокачественных данных

**Метрики**:
- Средний confidence автоматически исполненных заявок
- Win rate автоматических сделок
- Качество данных для обучения

### Риск 5: Проблемы с производительностью

**Описание**: Автоматическое исполнение может создать нагрузку на систему.

**Митигация**:
- Асинхронная обработка заявок
- Очередь для обработки
- Ограничение параллельных исполнений
- Мониторинг производительности

**Метрики**:
- Время обработки заявки
- Нагрузка на систему
- Количество параллельных исполнений

**Проблема**: Как обработать частичное исполнение (executedQuantity < quantity)?

**Решение**:
```javascript

async executePaperOrder(signal, executionResult = null) {
    let executedQuantity = signal.quantity;
    let executionPrice = signal.price;
    
    if (executionResult) {
        executedQuantity = executionResult.executedQuantity; // Может быть меньше signal.quantity
        executionPrice = executionResult.executedPrice;
    }
    
    // Обновить портфель только на фактически исполненное количество
    if (signal.action === 'BUY') {
        this.virtualPortfolio.cash -= executionPrice * executedQuantity;
        this.virtualPortfolio.positions[signal.figi] = 
            (this.virtualPortfolio.positions[signal.figi] || 0) + executedQuantity;
    } else {
        this.virtualPortfolio.cash += executionPrice * executedQuantity;
        this.virtualPortfolio.positions[signal.figi] -= executedQuantity;
    }
    
    // Обновить заявку с фактическим количеством
    tradingRequest.actualAmount = executionPrice * executedQuantity;
    tradingRequest.actualQuantity = executedQuantity; // Новое поле
    
    // Если частичное исполнение, можно создать новую заявку на оставшееся количество
    if (executedQuantity < signal.quantity) {
        const remainingQuantity = signal.quantity - executedQuantity;
        LoggerService.info('Partial execution, remaining quantity', { 
            figi: signal.figi, 
            remaining: remainingQuantity 
        });
        // Опционально: создать новую заявку на оставшееся количество
    }
}
```

#### 6. Расчет PnL для автоматически исполненных заявок

**Проблема**: Неясно, как рассчитывается PnL для BUY заявок (позиция еще не закрыта).

**Решение**: 
- Для **BUY**: PnL = 0 (позиция открыта, PnL будет рассчитан при закрытии)
- Для **SELL**: PnL = ((sellPrice - buyPrice) / buyPrice) * 100
- Использовать `actualPrice` из `TradingRequest` (с учетом спреда и проскальзывания)

```javascript
// В AutoPaperTradingService.autoExecuteRequest()
let calculatedPnL = 0;
if (tradingRequest.action === 'SELL') {
    // Найти соответствующую BUY заявку
    const buyRequest = await TradingRequest.findOne({
        where: {
            figi: tradingRequest.figi,
            action: 'BUY',
            status: 'EXECUTED',
            executedAt: { [Op.lt]: tradingRequest.executedAt }
        },
        order: [['executedAt', 'DESC']]
    });
    
    if (buyRequest && buyRequest.actualPrice) {
        const buyPrice = buyRequest.actualPrice;
        const sellPrice = executionResult.executedPrice;
        calculatedPnL = ((sellPrice - buyPrice) / buyPrice) * 100; // В процентах
    }
}
```
