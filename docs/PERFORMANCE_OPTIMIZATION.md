# Оптимизация производительности на удаленном сервере

## Проблемы и решения

### 1. N+1 проблема в запросах к БД ✅ ИСПРАВЛЕНО

**Проблема:** В `portfolio-routes.js` выполнялись запросы к БД внутри цикла для каждого FIGI.

**Решение:** Загружаем все заявки одним запросом перед циклом и группируем по FIGI.

**До:**
```javascript
for (const figi of allFigis) {
    const buyRequests = await TradingRequest.findAll({ where: { figi, ... } });
    const sellRequests = await TradingRequest.findAll({ where: { figi, ... } });
}
```

**После:**
```javascript
const allBuyRequests = await TradingRequest.findAll({
    where: { figi: { [Op.in]: allFigis }, ... }
});
// Группируем по FIGI и используем в цикле
```

### 2. Задержки между запросами к внешним API

**Проблема:** В коде есть задержки 1.5-2 секунды между запросами к Tinkoff API и News API.

**Рекомендации:**
- Использовать параллельные запросы где возможно
- Кешировать результаты агрессивнее
- Использовать batch-запросы API

**Места для оптимизации:**
- `CacheService.fetchCandlesRangeBatched` - задержка 1.5 сек между запросами
- `SchedulerService.performLimitedNewsUpdate` - задержка 1 сек между запросами
- `TinkoffApiService` - базовая задержка 500ms

### 3. Конфигурация пула соединений БД

**Текущая конфигурация** (`server/src/config/database.js`):
```javascript
pool: {
    max: 15,
    min: 2,
    acquire: 60000,  // 60 секунд
    idle: 300000,    // 5 минут
    evict: 5000
}
```

**Рекомендации:**
- Для удаленного сервера можно увеличить `max` до 20-25
- Уменьшить `acquire` до 30000 (30 сек) для быстрого обнаружения проблем
- Проверить, что соединения освобождаются правильно

### 4. Множественные вызовы `sequelize.authenticate()`

**Проблема:** В коде есть 16+ мест, где вызывается `sequelize.authenticate()`.

**Рекомендации:**
- Использовать `DatabaseConnectionManager.acquireConnection()` вместо прямых вызовов
- Кешировать результат проверки соединения
- Использовать пул соединений вместо проверки каждый раз

### 5. Синхронные операции с файловой системой

**Проблема:** Сохранение моделей может блокировать event loop.

**Рекомендации:**
- Убедиться, что все операции с файлами асинхронные (используется `fs/promises`)
- Рассмотреть использование очереди для сохранения моделей
- Использовать streaming для больших файлов

### 6. Сетевая задержка

**Проблема:** На удаленном сервере может быть высокая задержка к внешним API.

**Рекомендации:**
- Использовать CDN для статических ресурсов
- Кешировать агрессивнее результаты внешних API
- Использовать connection pooling для HTTP-запросов
- Рассмотреть использование прокси-сервера ближе к API

### 7. Логирование

**Проблема:** Избыточное логирование может замедлять работу.

**Рекомендации:**
- Использовать уровни логирования (error, warn, info, debug)
- В production использовать только error и warn
- Рассмотреть асинхронное логирование
- Использовать structured logging для лучшей производительности

## Диагностика

### Скрипт диагностики

Используйте `scripts/diagnose-performance.sh` для проверки:
- Использование ресурсов Docker контейнеров
- Активные соединения к БД
- Медленные запросы
- Блокировки в БД
- Размер БД и таблиц
- Сетевая задержка

### Мониторинг в реальном времени

1. **Проверка медленных запросов:**
```sql
SELECT pid, now() - pg_stat_activity.query_start AS duration, query 
FROM pg_stat_activity 
WHERE (now() - pg_stat_activity.query_start) > interval '1 second' 
AND state = 'active' 
ORDER BY duration DESC;
```

2. **Проверка блокировок:**
```sql
SELECT * FROM pg_locks WHERE NOT granted;
```

3. **Статистика пула соединений:**
```bash
curl http://localhost:3001/api/system/health
```

## Дополнительные рекомендации

### Индексы БД

Убедитесь, что есть индексы на:
- `TradingRequest.figi` + `action` + `status`
- `CachedCandle.figi` + `interval` + `time`
- `CachedInstrument.figi`
- Все внешние ключи

### Кеширование

- Использовать Redis для кеширования часто запрашиваемых данных
- Кешировать результаты анализа портфеля
- Кешировать прогнозы и рекомендации

### Оптимизация запросов

- Использовать `SELECT` только нужных полей
- Избегать `SELECT *`
- Использовать `LIMIT` где возможно
- Использовать `JOIN` вместо множественных запросов

### Мониторинг

- Настроить APM (Application Performance Monitoring)
- Мониторить метрики БД (pg_stat_statements)
- Настроить алерты на медленные запросы
- Мониторить использование памяти и CPU

## Метрики для отслеживания

1. **Время ответа API:**
   - Среднее время ответа
   - 95-й и 99-й перцентили
   - Количество медленных запросов (>1 сек)

2. **База данных:**
   - Количество активных соединений
   - Время выполнения запросов
   - Количество блокировок
   - Размер БД

3. **Внешние API:**
   - Время ответа Tinkoff API
   - Время ответа News API
   - Количество ошибок и таймаутов

4. **Системные ресурсы:**
   - Использование CPU
   - Использование памяти
   - Использование диска
   - Сетевая активность
