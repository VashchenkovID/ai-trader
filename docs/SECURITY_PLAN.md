# План усиления защиты AI Trader

Документ фиксирует приоритеты и шаги по снижению рисков для API и окружения. Основан на текущей архитектуре FastAPI (`server_fastapi`), публичных эндпоинтах и наблюдаемом фоновом сканировании (запросы к `/.env`, `/.git`, типовым `/api/*` и т.д.).

## 1. Цели и границы

- **Цель:** уменьшить поверхность атаки, ограничить ущерб при компрометации, сохранить работоспособность легитимных клиентов (фронтенд, health-checks).
- **Вне scope этого плана:** сертификация, полный pen-test (заказывается отдельно), защита рабочих станций разработчиков.

## 2. Краткая модель угроз

| Угроза | Пример | Релевантность |
|--------|--------|----------------|
| Массовое сканирование | GET к несуществующим путям, 404 | Высокая (фон интернета) |
| Подбор секретов / утечки | Доступ к `.env`, OpenAPI без ограничений | Средняя при ошибочном деплое |
| DoS / перегруз | Много запросов с одного IP | Средняя при публичном IP |
| Неверная интерпретация мониторинга | Ложные critical по `errorRate` на мусорных путях | Операционная (см. п. 6) |

## 3. Слои защиты (что делать и где)

### 3.1 Сеть и инфраструктура

- По возможности **не выставлять** приложение в интернет без reverse proxy (Nginx, Caddy, облачный LB).
- Для админки, БД, внутренних метрик — **только приватная сеть / VPN / allowlist IP**.
- Включить **TLS** на edge; на приложении в контейнере часто достаточно HTTP за прокси с корректными заголовками доверия.

### 3.2 Edge (прокси / WAF / CDN)

- **Rate limiting** по IP (и при необходимости по путям): снижает шум от сканеров и простой DoS.
- Опционально: **WAF** (Cloudflare, AWS WAF, аналоги) для типовых сигнатур.
- Ограничить размер тела запроса и таймауты на прокси.

### 3.3 Приложение (FastAPI)

Текущие точки внимания в репозитории:

- Публичные маршруты на корне приложения: **`GET /health`**, **`GET /metrics`** (`server_fastapi/app/main.py`). Для production целесообразно:
  - оставить `/health` доступным для балансировщика (или вынести liveness на отдельный порт/путь по политике);
  - **ограничить или убрать публичный доступ** к `/metrics` (только внутренняя сеть, либо auth на прокси).
- **CORS** уже ограничен списком origin (`FRONTEND_URL` + localhost) — в проде держать список минимальным.
- В настройках есть **`DISABLE_RATE_LIMIT` / `RATE_LIMIT_MAX`** (`server_fastapi/app/core/config.py`); имеет смысл **подключить реальный лимит** на HTTP-слой (middleware или прокси) и задать разумные значения для анонимного трафика.
- Рассмотреть **`TrustedHostMiddleware`** (или эквивалент на прокси), если есть риск подмены заголовка `Host`.

### 3.4 Секреты и конфигурация

- **`JWT_SECRET`**, **`USER_PASSWORD`**, токены брокера и БД — только из secret manager / env, **никогда** в git.
- Убедиться, что в артефактах деплоя **нет** `.env` и каталога `.git` в web-root.
- Ротация секретов при утечке или увольнении; отдельные учётки для prod/staging.

### 3.5 Аутентификация и авторизация API

- Все операции с деньгами, персональными данными и изменением состояния — **строго за проверкой токена/ролей**.
- Периодически проверять отсутствие «забытых» публичных ручек на `/api/...`.

### 3.6 Наблюдаемость и алерты

Сейчас метрики считают ошибкой любой ответ **`status_code >= 400`** (`server_fastapi/app/core/metrics.py`), а алерты по error rate строятся по каждому ключу маршрута (`server_fastapi/app/api/v1/monitoring.py`). Из-за этого **скан с 404 раздувает critical**.

План улучшений (без обязательного порядка):

- Не считать **404 по несовпавшим маршрутам** как SLO-ошибку **или** агрегировать unknown в один бакет.
- Не создавать алерт при малом **`count`** по маршруту (минимальный порог выборки).
- Разделить метрики: **5xx** (доступность) vs **4xx** (клиент/скан).

## 4. Фазы внедрения

### Фаза A — быстрые меры (низкая стоимость)

- Проверить прод-конфиг: секреты, отсутствие debug, закрытие `/metrics` снаружи.
- Включить rate limit на **edge** или в приложении для анонимных запросов.
- Скорректировать логику метрик/алертов, чтобы скан не маскировал под «падение сервиса».

### Фаза B — устойчивость

- WAF или расширенные правила прокси.
- Политика заголовков безопасности (где уместно для API + статики фронта).
- Регулярные обновления зависимостей и образов.

### Фаза C — зрелость

- Периодический аудит прав доступа, таблица ответственности за инциденты.
- По необходимости — внешний pen-test и доработка по отчёту.

## 5. Чеклист перед выкладкой в публичный интернет

- [ ] TLS и корректные DNS.
- [ ] Секреты не в репозитории; сильные значения для JWT и паролей.
- [ ] `/metrics` и админские пути недоступны анонимно из интернета.
- [ ] Rate limiting на edge или в приложении.
- [ ] CORS содержит только реальные origin продакшена.
- [ ] Мониторинг реагирует на **5xx** и ключевые бизнес-маршруты, а не на каждый случайный URL сканера.
- [ ] Резервное копирование БД и план восстановления.

## 6. Связанные файлы в репозитории

| Область | Файлы |
|---------|--------|
| Точка входа, CORS, `/health`, `/metrics` | `server_fastapi/app/main.py` |
| Метрики по запросам | `server_fastapi/app/core/middleware.py`, `server_fastapi/app/core/metrics.py` |
| Алерты мониторинга | `server_fastapi/app/api/v1/monitoring.py` |
| Настройки | `server_fastapi/app/core/config.py`, `server_fastapi/.env.example` |

## 7. Реализовано в коде (бэкенд)

- **Rate limit:** sliding window по IP в `server_fastapi/app/core/middleware.py`; `DISABLE_RATE_LIMIT`, `RATE_LIMIT_MAX`, `RATE_LIMIT_WINDOW_SECONDS`; health-пробы в allowlist.
- **Метрики:** раздельные `serverErrorCount` / `clientErrorCount` и доли в snapshot; неизвестные пути — ключ `GET <unmatched>` (и аналогично для других методов).
- **SLO-алерты:** только по `serverErrorRate` и при `count >= SLO_ALERT_MIN_SAMPLES` (`server_fastapi/app/api/v1/monitoring.py`).
- **Корневой `/metrics`:** `EXPOSE_ROOT_METRICS`, опционально `METRICS_AUTH_TOKEN` + заголовок `X-Metrics-Token` или `Authorization: Bearer` (`server_fastapi/app/core/metrics_access.py`).
- **Trusted Host:** при непустом `TRUSTED_HOSTS` подключается `TrustedHostMiddleware` в `server_fastapi/app/main.py`.
