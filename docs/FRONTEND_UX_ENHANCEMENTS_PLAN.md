## A. Главная (`/dashboard`): три операционные кнопки

**Цель:** с главной страницы запускать типовые фоновые операции без Postman.

| Кнопка (как в ТЗ) | Предлагаемая привязка к API (уточнить у бэкенда) |
| ----------------- | ------------------------------------------------ |
| Полная загрузка БД | `SystemService.systemDataFullSyncYearApiV1SystemDataFullSyncYearPost` — `POST /api/v1/system/data/full-sync-year` (полная загрузка данных за год). Если нужен другой смысл «полной БД» — добавить/переименовать эндпоинт или вынести отдельный trigger. |
| Ежедневное обновление кеша | `SystemService.systemCacheUpdateApiV1SystemCacheUpdatePost` — `POST /api/v1/system/cache/update`. |
| Провести анализ | Кандидаты: `SystemService.analysisMarketPortfolioApiV1SystemAnalysisMarketPortfolioPost` (`POST /api/v1/system/analysis/market-portfolio`), либо сценарий из `PortfolioAnalyzerService` / `RecommendationPipelineService` — **зафиксировать один каноничный сценарий «анализ» для дашборда**. |

**Реализация:**

- Три `Button` (или группа с подтверждением `Dialog` для тяжёлых операций).
- После `POST` показывать `TriggerResponse` / envelope (task id, message) и подписку на обновления через существующий WebSocket (`systemStatusStore`) или polling `systemSchedulerStatus` / список задач.
- Ошибки — `apiErrorMessage`, блокировка двойного клика на время `loading`.
- Роли: при необходимости скрывать кнопки для не-админов (если появится флаг в `UserDTO` или отдельный эндпоинт прав).

**Критерий готовности:** пользователь видит понятный результат запуска (id задачи, «принято в работу») и может отследить завершение в блоке «Система» (см. п. B).

## B. Блок «Система» на дашборде: подробнее о задачах

**Цель:** не только `taskType — status`, а понятная сводка по последним операциям.

**Данные:** в `systemStatusStore` у задач уже есть поля `queuedAt`, `startedAt`, `finishedAt`, `error`, `result` (см. тип `TaskRecord`). Сейчас UI выводит минимум.

**Реализация:**

- Расширить список/карточки: длительность, время окончания, краткий текст ошибки, **краткое человекочитаемое резюме `result`** (не сырой JSON в первую очередь).
- Для неизвестных типов задач — fallback: форматированный JSON в `Accordion` / «Подробнее».
- Опционально: ссылка «Все задачи» на `/monitoring/alerts` или отдельный лог, если появится API.

**Критерий готовности:** по одной задаче видно, *что* выполнялось, *когда* завершилось, *успех или причина сбоя*, без обязательного чтения JSON.

## C. Шапка shell: отображать `fullName`, а не логин

**Цель:** справа сверху (desktop-полоса «Срез» и подзаголовок mobile AppBar) показывать **`profile.fullName`** из `tradingCoreStore`.

**Реализация:**

- Заменить `profile.username` на `profile.fullName?.trim() || profile.username` (fallback, если ФИО пустое).
- Проверить контраст и обрезку длинных строк (`noWrap` + `title` tooltip при необходимости — тогда задействовать п. Tooltip из DS).

**Критерий готовности:** в UI отображается понятное имя пользователя согласно данным сессии.

## D. Виртуальные портфели: конфиг порогов без сырого JSON

**Цель:** секция «Конфигурация порогов (по профилю)» — таблицы/карточки с подписями полей, единицами измерения и тултипами, а не один блок `JSON.stringify`.

**Реализация:**

- Зафиксировать контракт ответа `getVirtualProfilesConfig` (или актуального метода) в TypeScript-типе / zod-схеме.
- Смаппить известные ключи на русские подписи и форматтеры (проценты, рубли, дни).
- Неизвестные ключи — строка «Доп. параметр» + значение; опционально «Показать как JSON» для отладки.
- Согласовать с бэкендом стабильные имена полей; при изменении API — обновить маппинг.

**Критерий готовности:** типичный пользователь настраивает пороги без чтения JSON.

## E. Страница «Риск»: вместо JSON — структурированный UI

**Цель:** статус риска, лимиты, preflight — в виде секций, списков, метрик и пояснений на русском.

**Объём:**

- Текущие блоки сырого JSON: `RiskService` (status, limits), `PreflightCheckService` (status, results).
- Для каждого поля из ответа: заголовок, описание (из документации бэкенда или `docs/BACKEND_BUSINESS_LOGIC.md`), формат значения.
- Сохранить «Сырой JSON» свёрнутым (developer mode) по желанию.

**Критерий готовности:** основные сценарии читаются без знания структуры API.

## F. Страница «Производительность»: вместо JSON — структурированный UI

**Цель:** то же, что в п. E, для данных `PerformanceService` / системных метрик производительности, которые сейчас или будут отображаться на `/performance`.

**Реализация:**

- Инвентаризация эндпоинтов страницы и полей ответа.
- Общие компоненты с п. E (например `KeyValueSection`, `MetricCard`, `StatusChip`) вынести в `frontend/src/components/ops/` или рядом с дашбордом, чтобы не дублировать.

**Критерий готовности:** ключевые KPI и статусы видны с подписями; JSON только как fallback.

## Зависимости и риски

1. **Семантика кнопок дашборда** должна совпадать с бэкендом (особенно «полная загрузка БД» vs `full-sync-year`).
2. **Форма `result` у задач** может различаться по `taskType` — потребуется реестр форматтеров или универсальные правила.
3. **Риск/Производительность:** без стабильного контракта OpenAPI легко сломать маппинг; держать типы рядом с `generate:api` или явными DTO.
