## 🔍 Текущая ситуация

### Рабочий процесс пользователя

**Цепочка операций (для покупки):**
1. 📊 Анализ рекомендаций в приложении
2. 📝 Создание заявки на покупку (`TradingRequest`) - заявка содержит `strategyId`
3. ✅ Одобрение заявки (status: `APPROVED`) - заявка сохраняется с `strategyId`
4. 📱 Покупка акций через внешнее приложение Т-Инвест (вне нашего приложения)
5. 🔄 Синхронизация портфеля - **ЗДЕСЬ НУЖНА РЕАЛИЗАЦИЯ**

**Цепочка операций (для продажи):**
1. 📊 Анализ позиции в портфеле
2. 📝 Создание заявки на продажу (`TradingRequest` с `action: 'SELL'`) - заявка содержит `strategyId`
3. ✅ Одобрение заявки (status: `APPROVED`) - заявка сохраняется с `strategyId`
4. 📱 Продажа акций через внешнее приложение Т-Инвест (вне нашего приложения)
5. 🔄 Синхронизация портфеля - **ТА ЖЕ ЛОГИКА**, но обработка уменьшения/закрытия позиции

**Задача синхронизации:**
- Сравнить портфель "до" и "после" синхронизации
- Найти изменения позиций:
  - **Новые позиции** (появились или количество увеличилось) → заявки на **покупку** (BUY)
  - **Уменьшенные/закрытые позиции** (количество уменьшилось или позиция закрыта) → заявки на **продажу** (SELL)
- Найти недавно одобренные заявки (`APPROVED` или `EXECUTED`)
- Сопоставить изменения позиций с заявками по `FIGI` и времени
- **Для покупки:** Создать `PositionStrategy` (или обновить существующий)
- **Для продажи:** Обновить/закрыть существующий `PositionStrategy`

### Существующая архитектура

#### 1. Модели данных
- **`RealPortfolio`** - хранит реальный портфель из брокера
  - Формат позиций: `{FIGI: quantity}` (JSON)
  - Синхронизация: через `TinkoffApiService.getPortfolio()`
  
- **`VirtualPortfolio`** - виртуальный портфель для paper trading
  - Формат позиций: `{FIGI: quantity}` (JSON)
  
- **`TradingStrategy`** - торговые стратегии (conservative, moderate, aggressive)
  - Содержит параметры: `budgetAllocation`, `minConfidence`, `minScore`, `stopLoss`, `takeProfit`
  
- **`PortfolioAllocation`** - распределение бюджета по стратегиям
  - `allocatedAmount` - выделенная сумма
  - `usedAmount` - использованная сумма
  
- **`PositionStrategy`** - связь позиций со стратегиями
  - Связывает `TradingRequest` (positionId) со `TradingStrategy` (strategyId)
  - Создается при создании TradingRequest (нужно изменять)
  
- **`TradingRequest`** - торговые заявки
  - Содержит `strategyId` (прямая связь) ✅
  - Статусы: PENDING, APPROVED, EXECUTED, REJECTED, CANCELLED
  - `approvedAt` - время одобрения заявки ✅

#### 2. Текущие процессы синхронизации

**✅ Что работает:**
- При создании `TradingRequest` автоматически создается `PositionStrategy` (для paper trading)
- Реальный портфель обновляется через `TradingEngine.getRealPortfolioValue()`
- Позиции из брокера сохраняются в `RealPortfolio`
- При одобрении заявки (`approveRequest`) сохраняется `strategyId`

**❌ Что не работает:**
- После покупки акций через внешнее приложение нет связи позиции со стратегией
- При синхронизации портфеля новые позиции не сопоставляются с одобренными заявками
- `PositionStrategy` создается при создании заявки, но для реальных позиций нужна синхронизация

## 🎯 Цели синхронизации

1. **Сопоставление новых/увеличенных позиций с заявками на покупку** - найти новые позиции и связать их со стратегией из заявки
2. **Сопоставление уменьшенных/закрытых позиций с заявками на продажу** - найти закрытые позиции и обновить/закрыть `PositionStrategy`
3. **Автоматическое создание PositionStrategy** - для новых позиций создавать связь со стратегией из `TradingRequest` (BUY)
4. **Автоматическое обновление/закрытие PositionStrategy** - для продажи обновлять количество или закрывать позицию
5. **Отслеживание изменений** позиций (увеличение/уменьшение количества)
6. **Обработка частичного исполнения** - если куплено/продано меньше акций, чем в заявке
7. **Обработка несоответствий** - позиции без заявок, заявки без позиций
8. **История изменений** для аудита

## 🔐 Обработка edge cases и конфликтов

### Сценарий 1: Несколько одобренных заявок на один FIGI
**Решение:** 
- Выбрать самую свежую заявку (по `approvedAt` DESC)
- Если есть уже созданный `PositionStrategy` для этого FIGI, не перезаписывать
- Логировать обнаружение нескольких заявок

### Сценарий 2: Частичное исполнение заявки
**Пример:** Заявка на 10 акций ВТБ, куплено 5 акций
**Решение:**
- Создать `PositionStrategy` с `actualQuantity: 5`
- В метаданных сохранить `requestedQuantity: 10`
- При следующей синхронизации проверить, не добавились ли еще акции

### Сценарий 3: Позиция появилась без соответствующей заявки
**Решение:**
- Добавить в результат синхронизации `unmatchedPositions[]`
- Не создавать `PositionStrategy` автоматически
- Уведомить пользователя о необходимости ручного назначения стратегии

### Сценарий 4: Заявка одобрена, но позиция не появилась
**Решение:**
- Добавить в результат `requestsWithoutPosition[]`
- Возможно, заявка еще не исполнена (пользователь еще не купил)
- Не создавать `PositionStrategy` (позиции нет)

### Сценарий 5: Позиция уже имеет PositionStrategy
**Решение:**
- Проверить наличие существующего `PositionStrategy` для FIGI
- Если есть и активен, не перезаписывать
- Если закрыт (`exitDate` установлен), создать новый для новой позиции

### Сценарий 6: Заявка на продажу (SELL action) - **ОБРАБАТЫВАЕТСЯ**
**Решение:** 
- Обрабатывать заявки с `action: 'SELL'` при синхронизации
- При уменьшении/закрытии позиции искать соответствующую SELL заявку
- Найти существующий `PositionStrategy` для FIGI
- Если позиция закрыта полностью → установить `exitDate`, рассчитать `resultPercent`
- Если позиция уменьшена → обновить метаданные о частичной продаже
- Если позиция уменьшилась, но SELL заявки нет → логировать несоответствие

### Сценарий 7: Заявка старше максимального времени поиска
**Решение:** 
- Искать только заявки за последние `maxLookbackHours` (по умолчанию 48)
- Заявки старше игнорируются (пользователь может увеличить `maxLookbackHours`)

### Сценарий 8: Продажа позиции, у которой нет PositionStrategy
**Решение:**
- Если позиция закрыта/уменьшена, но нет активного `PositionStrategy`
- Добавить в `unmatchedSells[]` (позиция закрыта без заявки)
- Уведомить пользователя о несоответствии
- Не создавать `PositionStrategy` для закрытой позиции

### Сценарий 9: Частичная продажа позиции
**Пример:** Было 10 акций ВТБ, продали 5, осталось 5
**Решение:**
- Найти SELL заявку на 5 или 10 акций
- Обновить `PositionStrategy`: записать в метаданные факт частичной продажи
- Позиция остается активной (не устанавливаем `exitDate`)
- При полной продаже → установить `exitDate` и рассчитать результат

## 🎯 Итоговый алгоритм синхронизации

### Шаг 1: Подготовка
1. Получить текущий портфель из `RealPortfolio` (снимок "до")
2. Получить актуальный портфель из брокера через `TradingEngine.getRealPortfolioValue()` ("после")
3. Получить одобренные заявки за последние 48 часов: `TradingRequest` со статусом `APPROVED` или `EXECUTED`

### Шаг 2: Поиск изменений
1. Найти новые позиции: `FIGI`, которых не было в снимке "до"
2. Найти увеличенные позиции: `FIGI`, где `quantity_after > quantity_before` → для **BUY заявок**
3. Найти уменьшенные позиции: `FIGI`, где `quantity_after < quantity_before` и `quantity_after > 0` → для **SELL заявок** (частичная продажа)
4. Найти закрытые позиции: `FIGI`, где было `quantity_before > 0`, а стало `quantity_after = 0` → для **SELL заявок** (полная продажа)
5. Сформировать списки:
   - `increasedPositions`: `[{figi, beforeQuantity, afterQuantity, addedQuantity}]` для BUY
   - `decreasedPositions`: `[{figi, beforeQuantity, afterQuantity, soldQuantity}]` для SELL (частичная)
   - `closedPositions`: `[{figi, beforeQuantity}]` для SELL (полная)

### Шаг 3: Сопоставление с заявками

**Для новых/увеличенных позиций (BUY):**
1. Найти заявки по `FIGI` из списка одобренных
2. Отфильтровать заявки с `action: 'BUY'`
3. Отсортировать по `approvedAt` (DESC) - самая свежая первая
4. Выбрать первую подходящую заявку (если есть несколько)

**Для уменьшенных/закрытых позиций (SELL):**
1. Найти заявки по `FIGI` из списка одобренных
2. Отфильтровать заявки с `action: 'SELL'`
3. Отсортировать по `approvedAt` (DESC) - самая свежая первая
4. Найти существующий активный `PositionStrategy` для этого `FIGI`
5. Выбрать первую подходящую SELL заявку (если есть несколько)

### Шаг 4: Создание/обновление связей

**Для новых/увеличенных позиций (BUY):**
1. Проверить, нет ли уже активного `PositionStrategy` для этого `FIGI`
2. Если нет → создать новый `PositionStrategy`:
   - `positionId` = `tradingRequest.id`
   - `strategyId` = `tradingRequest.strategyId`
   - `entryReason` = сохранить данные из заявки
   - `entryDate` = `tradingRequest.approvedAt` или `new Date()`
   - `quantity` = фактическое количество (может отличаться от заявки)
3. Если есть → обновить количество (если позиция увеличилась)
4. Обновить `PortfolioAllocation.usedAmount` для стратегии

**Для уменьшенных/закрытых позиций (SELL):**
1. Найти существующий активный `PositionStrategy` для `FIGI`
2. Если позиция **закрыта полностью** (`quantity_after === 0`):
   - Установить `exitDate` = `tradingRequest.approvedAt` или `new Date()`
   - Рассчитать `resultPercent` (прибыль/убыток в процентах)
   - Обновить метаданные о закрытии
3. Если позиция **уменьшена** (`quantity_after > 0`):
   - Обновить метаданные о частичной продаже
   - Позиция остается активной (не устанавливаем `exitDate`)
4. Обновить `PortfolioAllocation.usedAmount` для стратегии (уменьшить использованную сумму)

### Шаг 5: Обработка несоответствий
1. **Позиции без заявок:**
   - Новые/увеличенные позиции без BUY заявок → `unmatchedBuys[]`
   - Закрытые/уменьшенные позиции без SELL заявок → `unmatchedSells[]`
   - Закрытые позиции без активного `PositionStrategy` → `unmatchedClosed[]`
2. **Заявки без позиций:**
   - BUY заявки без соответствующих новых позиций → `requestsWithoutPosition[]`
   - SELL заявки без соответствующих изменений позиций → `sellRequestsWithoutPosition[]`
3. Вернуть результат с детальной информацией о всех несоответствиях

### Шаг 6: Сохранение результатов
1. Обновить `RealPortfolio` с новым снимком портфеля
2. Сохранить результаты синхронизации (опционально, в метаданные)
3. Отправить уведомление пользователю (если не `silent`)
